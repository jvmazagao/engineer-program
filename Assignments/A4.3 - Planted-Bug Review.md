# A4.3 — Planted-Bug Review

## Why

Your review hit rate is a measurable skill, not an identity. A PR with known defects is the only honest ruler: how many you catch — under time pressure, in your own stack — is your current level.

## Brief

**Session format — 45 min live review + 15 min debrief, engineer + mentor.**

**Before:** the mentor prepares a PR (~300–500 lines) on a scratch branch/repo, in the team's real stack, for a plausible feature. Seeded inside: ~8 issues spanning

- a correctness bug
- a concurrency issue
- an N+1 query
- an O(n²) pattern
- missing error handling
- a misleading name
- a missing test
- one design-level problem (e.g. leaky abstraction)

**The review:** 45 minutes, strictly timeboxed. The engineer writes *real PR comments* as they would at work — no running the code, no asking the mentor. Comments written as if a colleague would act on them tomorrow.

**Scoring:** 1 point per issue found (max 8) + comment quality 1–4 — does each comment state the *failure scenario*, or just "this looks wrong"? False positives don't deduct but get discussed.

**Debrief:** walk each missed issue; classify why it was missed — knowledge gap, reading order, or time pressure. Every miss becomes a checklist addition.

## Tasks

- [ ] Schedule the 60 min; mentor prepares the seeded PR in advance
- [ ] Engineer reviews within 45 min, comments written as at work
- [ ] Before the reveal: self-mark, listing the issues you believe you found
- [ ] Debrief: mentor reveals all seeds; classify each miss (knowledge / attention / time)
- [ ] Update your personal review checklist with ≥3 concrete additions
- [ ] Log findings in the review log (feeds A4.4)

## Acceptance criteria

- [ ] Session done under real time pressure with written comments
- [ ] Score sheet filled: issues found / 8, comment quality 1–4
- [ ] Every missed issue classified in the debrief
- [ ] Review checklist updated with ≥3 concrete additions
- [ ] Findings logged in the review log

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Issues found | ≤2 of 8 | 3–4 of 8 | 5–6 of 8 | 7–8 of 8 |
| Comment quality | "This looks wrong" | Names the line | States the failure scenario | Also proposes the fix or a test that would catch it |
| Triage | Commented on everything equally | Style-heavy | Time spent on correctness paths | Caught the design-level issue, not just the local bugs |
| Time use | Ran out with half the file unread | Uneven coverage | Covered the whole diff | Prioritized risky areas first (concurrency, queries, error paths) |

## Mentor review prompts

- "You found the N+1 but not the race. Is that knowledge or attention?"
- "Which comment would you have written identically under a real deadline?"
- "Was there a seeded issue you noticed but didn't comment on? Why not?"
