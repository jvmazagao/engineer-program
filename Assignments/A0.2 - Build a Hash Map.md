## Why

The hash map is the structure you use most every day and trust blindly. Building it once — collisions, load factor, resize — is what lets you explain why "O(1) lookup" sometimes isn't, and what actually happens when a map degrades.

## Brief

Create `dsa-from-scratch/01-hash-map/` and implement a `HashMap` without using the builtin dict for storage (a list of buckets is fine):

- **Separate chaining:** each bucket holds a list of `(key, value)` pairs
- **API:** `put(key, value)`, `get(key)` (return `None` when missing), `delete(key)`, `__contains__(key)`, `__len__`
- **Resize:** track `load_factor = size / bucket_count`; when it exceeds **0.75**, double the bucket count and rehash every entry
- **Hash function:** builtin `hash(key)` mod bucket count is fine; support string and integer keys

Benchmark against the builtin dict: insert then look up n = 1 000, 10 000, 100 000 random keys. Print a table.

## Tasks

- [ ] Implement `HashMap` with chaining and the full API above
- [ ] Resize at load factor 0.75, rehashing all entries
- [ ] Unit tests: empty map, missing key, overwrite same key, delete then get, forced collisions (many keys into few buckets), resize preserves every entry
- [ ] Benchmark script vs builtin dict, table printed for all three sizes
- [ ] In the submission note, answer:
  - Average and worst-case cost of `get` — and what input causes the worst case?
  - What does a resize cost, and why is `put` still "O(1) amortized"?
  - What does your language's builtin actually use (chaining? open addressing?), and how did the benchmark compare?

## Acceptance criteria

- [ ] Tests pass, including one that forces collisions and one that forces a resize
- [ ] No builtin dict used inside the implementation
- [ ] Benchmark table covers all three sizes for both implementations
- [ ] Average vs worst case explained correctly in your own words
