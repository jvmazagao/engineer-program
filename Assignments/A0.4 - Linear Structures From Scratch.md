# A0.4 — Linear Structures From Scratch

## Why

Stacks and queues are everywhere once you can see them: undo, DFS, task queues, parsing. Implementing them by hand — and knowing which end of the list each operation touches — is what makes the choice deliberate instead of "whatever the library has".

## Brief

Create `dsa-from-scratch/03-linear-structures/` and implement, from scratch:

- **Singly linked list:** `append`, `prepend`, `find(value)`, `delete(value)`, `reverse()` (in place), `__len__`, `__iter__`
- **Stack (LIFO):** `push`, `pop`, `peek` — all O(1)
- **Queue (FIFO):** `enqueue`, `dequeue` — both O(1) (a plain dynamic array makes `dequeue` O(n); don't)
- **Deque:** `add_front`, `add_back`, `remove_front`, `remove_back` — all O(1)

Then use **your own stack** (not the library's) to solve [[Valid Parentheses]]: `valid_parentheses(s) -> bool` for `()`, `[]`, `{}`.

Every operation's complexity should be true by design, not by accident — you'll be asked to point at the code that makes each one O(1).

## Tasks

- [ ] Implement the four structures with the APIs above
- [ ] Unit tests for each: empty structure, single element, operations in both orders, `reverse` on empty/list-of-one, pop/dequeue from empty (decide and document the behaviour)
- [ ] Implement `valid_parentheses` using your stack; tests: `"()"`, `"()[]{}"`, `"(]"`, `"([)]"`, `"{[]}"`, `""`, `"("`
- [ ] In the submission note, answer:
  - Why is `dequeue` on a plain dynamic array O(n), and how does your queue avoid it?
  - Walk through your `reverse()` with pointers on a 3-node list
  - What does your stack return on `pop` from empty, and why that choice?

## Acceptance criteria

- [ ] Tests pass for all four structures
- [ ] `push`/`pop`/`peek`, both deque ends, and both queue ends are O(1) by construction — and you can point at why
- [ ] `valid_parentheses` uses your stack and passes all listed cases
- [ ] Empty-structure behaviour documented and tested, not undefined

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Correctness | Tests missing or failing | Happy path only | Edge cases covered | Edge cases + clean idiomatic code |
| Complexity discipline | Some ops accidentally O(n) | Mostly O(1), can't say why | All O(1) ops correct, reasons given | Also explains the memory cost of each design |
| Valid Parentheses | Not solved or uses builtin stack | Works, no reasoning | Correct with explanation | Explains the stack invariant and the failure mode |
| API and tests | No tests | Trivial tests | Edge cases tested | Empty-behaviour decisions documented and justified |

## Mentor review prompts

- "Where does our codebase depend on ordering — a queue, a retry stack, an undo path?"
