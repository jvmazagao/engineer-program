## Why

Knowing patterns and performing under observation are different skills. This is the first rehearsal of the thing Phase 0 exists for: receiving an unseen problem, thinking aloud, and landing a correct solution while someone watches.

## Brief

A 45-minute live session. **Mentor = interviewer, engineer = candidate.**

**Problem selection:** mentor picks **2 unseen problems — 1 Easy, 1 Medium** — from the weeks 3–8 topics: arrays, hashing, two pointers, sliding window, linked lists, stacks/queues, recursion, sorting, binary search. "Unseen" means not in the pattern journal — the engineer sends their `NOTES.md` index before the session and the mentor checks against it.

**Session format:**

| Time | What happens |
|---|---|
| 0–5 min | Setup. Plain editor or shared doc, no autocomplete. Mentor states the rules. |
| 5–23 min | Problem 1. Candidate clarifies → proposes approach → states complexity → codes → tests with an example. |
| 23–40 min | Problem 2, same flow. |
| 40–45 min | Feedback: one strength, one focus area. Scores recorded. |

**Roles:** the candidate thinks aloud from minute 0 — silent work is penalized. The mentor stays in character: restates nothing, gives a hint only after 5+ minutes of stalling, and records every hint given (hints lower the score for that row). The mentor does not touch the code.

**Scoring:** mentor scores each rubric row 1–4 independently during the session, then walks the scores back with the candidate. Average and problems used go in the submission note.

## Tasks

- [ ] Send `NOTES.md` index to the mentor ≥ 24 h before the session
- [ ] Hold the 45-min session
- [ ] Think aloud for both problems; state complexity before coding each
- [ ] Test each solution with a concrete example before declaring done
- [ ] Record problems used, hints given, and per-row scores in the submission note
- [ ] Add the mentor's focus area to next week's problem list

## Acceptance criteria

- [ ] Session held at 45 minutes with both problems unseen
- [ ] All 5 rubric rows scored 1–4 with a recorded average
- [ ] Complexity stated aloud before code for both problems
- [ ] Hints (if any) recorded, not forgotten
- [ ] Submission note includes problems used and the feedback outcome

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Clarifying questions | Dives straight into code | One generic question | Asks about input size, edge cases, constraints | Questions visibly shape the chosen approach |
| Approach | No plan; code first | Brute force only, defended too long | Names a pattern, states a plan | Compares two approaches and picks with reasons |
| Complexity | Not stated or wrong | Stated after prompting | Correct, stated unprompted before coding | Also covers space and the worst-case input |
| Correctness | Not working | Works on the example only | Passes edge cases | Clean, near-final code on first pass |
| Testing | None | Traces one happy path | Tests an edge case unprompted | Finds own bug while testing and fixes it |

## Mentor review prompts

- "What was your first question, and what did it change about your plan?"
