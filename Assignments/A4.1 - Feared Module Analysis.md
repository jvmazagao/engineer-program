# A4.1 — Feared Module Analysis

## Why

Every team has a module nobody wants to touch — tickets get scoped around it, and the fear compounds. Seniors don't avoid the feared module; they diagnose *why* it's feared and make it safe to change.

## Brief

Pick the module your team avoids — the one where estimates double "just in case".

**Diagnose** it with Ousterhout's three symptoms, each scored with concrete evidence:

1. **Change amplification** — one logical change touches how many modules? Measure it: pick ≥3 past changes in the module's area, link the tickets/PRs, count files touched
2. **Cognitive load** — how much must a reader know before a one-line change is safe?
3. **Unknown unknowns** — what could break that isn't obvious from the code?

**Propose a boundary**: what should this module *hide* (information hiding)? Which interface can be deepened — simple to use, complex behavior behind it? Sketch the new interface and what moves out. Say what you would *not* change and why.

**Pin the behavior**: before any refactor, write characterization tests that lock in current behavior as-is — including the weird parts. Each surprising pinned behavior gets a comment explaining it's intentional and why. These tests are the safety net for A4.2.

Review the analysis and boundary with the mentor before starting any refactor.

## Tasks

- [ ] Name the module and the fear ("we don't touch X because…")
- [ ] Collect ≥3 past painful changes; measure the amplification (files/PRs touched)
- [ ] Score all three Ousterhout symptoms with evidence
- [ ] Sketch the proposed boundary: what it hides, the new interface, what moves out
- [ ] Write characterization tests pinning current behavior, including edge cases that look like bugs
- [ ] Merge the tests green; record which critical paths they cover
- [ ] Review analysis + boundary with the mentor (gate for A4.2)

## Acceptance criteria

- [ ] Analysis references ≥3 real past changes with links
- [ ] Each symptom scored with a concrete example, not adjectives
- [ ] Proposed boundary names what the module hides and shows the new interface
- [ ] Characterization tests merged and green, covering the paths any refactor would break
- [ ] ≥1 test documents a currently-surprising behavior with an explanatory comment
- [ ] Mentor sign-off on the boundary before refactor work starts

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Diagnosis | "It's messy" | Generic complexity claims | Symptoms scored with real examples | Amplification quantified (files/PRs per change) across time |
| Boundary proposal | Rewrite everything | Moves code around | Names the information to hide + a deep interface | Shows the top 3 painful changes getting cheap under the new boundary |
| Characterization tests | None | A few happy paths | Critical paths pinned | Weird behaviors pinned with explanations a future reader can trust |
| Judgment | Big-bang rewrite appetite | Abstract ideals | Proportionate to real pain | Explicitly says what *not* to change, and why |

## Mentor review prompts

- "Which symptom hurts most day to day? Is the proposed boundary actually aimed at it?"
- "Show me the test pinning behavior everyone thinks is a bug. Why keep it?"
- "What's the smallest change that removes the most fear?"

## Stretch 🔸
