# A1.1 — Runtime Explainer

## Why

Phase 1 starts by refusing to treat your stack as magic. If you can't say where 100 concurrent requests physically live while 4 are running, you can't debug latency, capacity, or "the pool is exhausted" alerts — you can only restart things.

## Brief

Pick your **main production language** — the one your services at work are written in. Deliver three artifacts:

1. **One diagram, drawn by hand** (photo of paper, Excalidraw, whatever — *you* draw it, no pasting from blogs): the execution model of one process. What exists per process — interpreter, event loop or thread pool, scheduler, GC, GIL if your language has one. Add the path of one request: arrival → framework → handler → response, marking where it waits and where it runs.
2. **A one-pager** (`RUNTIME.md`), plain prose: What blocks in this runtime? What's CPU-bound vs I/O-bound here, and what does each do to throughput? How does your framework pick up a request — thread per request? event loop with async handlers? worker pool of how many, configured where?
3. **A tiny program** in `dsa-from-scratch/08-runtime-explainer/` that demonstrates starvation: an endpoint whose handler makes a **blocking** call (`time.sleep(2)` or equivalent) and a sibling that awaits properly (`await asyncio.sleep(2)` / non-blocking equivalent). Fire ~20 concurrent requests at each; report measured latency for both in a table. The blocking version should serialize — show it, don't assert it.

Include how to run the demo and the exact numbers. If your runtime is thread-based rather than event-loop-based, starve the pool instead (e.g., saturate a 4-worker pool with blocked handlers).

## Acceptance criteria

- [ ] Diagram is your own and labels every box you can't explain yet (that's useful signal)
- [ ] One-pager correctly states what blocks in your runtime — no blog-copy language
- [ ] Demo runs as documented; blocking version measurably serializes, numbers reported
- [ ] Latency table has both handlers under the same load conditions
- [ ] Real (not hypothetical) CPU-bound and I/O-bound examples from your work

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Accuracy | Wrong model (e.g., "async makes it fast" with no mechanism) | Right terms, confused mechanics | Correct model for the main path | Includes what happens on a slow downstream call and on GC |
| Diagram | Copied or decorative | Structure right, request path missing | Process + request path correct | Also marks waiting vs running and pool sizes |
| Demo | Doesn't run | Runs, no measurement | Measured, blocking serializes | Same-conditions comparison + explains the measured shape |
| Clarity | For nobody but you | Correct but dense | A teammate could follow it | A teammate *would* repeat it — concrete and short |
