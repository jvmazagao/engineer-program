# A3.2 — SLOs and Burn-Rate Alerts

## Why

Alerting on causes means pages for things users never notice, and silence for things they do. SLOs flip this: alert on user-visible symptoms, and let the error budget decide what's urgent.

## Brief

From the A3.1 audit, pick the 2–3 user-facing flows that matter most. For each:

1. **SLI** — the measurement, defined precisely: formula, data source, window. Ideally measured where the user feels it, not inside the service
2. **Target** — pick it and justify it: what does 99.9% actually mean for *this* user?
3. **Error budget** — convert the target to concrete units: minutes of failure/slowness per 30 days
4. **Burn-rate alerts** — implement fast + slow windows per the SRE Workbook pattern (e.g. fast: 14.4× burn over 1h with a 5m window; slow: 6× over 6h with a 30m — adapt to what your alerting stack supports)

Then the deletion pass: for **every existing alert** on the service, decide keep / rewrite as burn-rate / delete, with a recorded reason for each. Net alert count should not go up.

This is at-work: alerts must actually be merged into the real alerting system, not proposed in a doc. Track for ≥2 weeks afterwards and report pages received and false positives honestly.

## Tasks

- [ ] Pick 2–3 flows from the audit; write SLI definitions (formula, source, window)
- [ ] Set targets with per-flow justification; compute error budgets in minutes per 30 days
- [ ] Implement burn-rate alerts (fast + slow); merge them for real
- [ ] Decide keep/rewrite/delete for every existing alert; record the reason per alert
- [ ] Ensure every remaining page is actionable and has a runbook (or a tracked placeholder)
- [ ] Track ≥2 weeks: pages received, false positives, budget consumed
- [ ] Write the SLO doc / README section and share it with the team

## Acceptance criteria

- [ ] 2–3 SLOs defined with explicit SLI formulas and targets
- [ ] Error budgets computed in concrete units (minutes per 30 days)
- [ ] Burn-rate alerts live in the real alerting system — config linked
- [ ] Net alert count did not increase; every removed alert has a recorded reason
- [ ] ≥2 weeks of data reported, including the false-positive rate

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| SLI quality | Vague ("it works") | Technical metric users never feel | User-facing and measurable | Measured at the edge/client where users experience it |
| Targets | Copy-pasted 99.9 everywhere | Justified once | Justified per flow against real user expectations | Budget tied to a decision: what gets paused when it's spent |
| Alerting | More alerts than before | Burn-rate configured but untested | Tested against historical data | Would have caught past real incidents with fewer pages than the old set |
| Hygiene | Alerts without runbooks | Runbooks stubbed | Every page actionable | Zero non-actionable alerts remain on the service |
