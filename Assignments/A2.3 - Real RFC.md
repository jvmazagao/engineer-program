# A2.3 — Real RFC

## Why

Practice designs are safe; an RFC at work has real reviewers, real politics, and real consequences. Writing one that survives review — and recording the decision it produced — is the core senior writing skill.

## Brief

Pick a real upcoming change at work, ambiguous enough that two reasonable engineers would design it differently, and likely to actually ship (or be explicitly rejected). Confirm with your manager it's worth a doc.

Structure — all ten sections, none optional:

**Context · Problem · Goals · Non-goals · Proposal · Alternatives · Risks · Rollout · Observability · Open questions**

Process, in order:

1. Draft the RFC with all ten sections
2. **Early feedback pass**: one senior/staff engineer reads the draft *before* the wide review. Note what changed as a result
3. Open the review (doc comments or a meeting). Respond to every substantive comment in writing
4. After the decision: write a short **ADR** — decision, date, alternatives rejected, main reason. Link it from the RFC
5. Log the RFC in your Brag Document with links

## Tasks

- [ ] Pick the change; confirm with your manager it's real and doc-worthy
- [ ] Draft with all ten sections; non-goals and alternatives included even if awkward
- [ ] Early feedback from one senior/staff before wide review; record what it changed
- [ ] Run the review; every substantive comment gets a written response
- [ ] Write the ADR once the decision lands; link it from the RFC
- [ ] Add the RFC + ADR to the Brag Document

## Acceptance criteria

- [ ] RFC has all ten sections; Open questions is non-empty at review time
- [ ] At least one alternative is described fairly enough that its advocate would agree
- [ ] Early feedback happened before the wide review and measurably changed the draft
- [ ] Every substantive review comment has a written response
- [ ] ADR exists and makes sense to a reader in 6 months with no context

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Problem framing | Jumps to the solution | Problem stated | Problem stated with quantified impact | Non-goals prevent the obvious scope creep before it starts |
| Proposal | Vague hand-waving | Works for the happy path | Concrete: interfaces, data, migration path | Executable by the team without the author in the room |
| Alternatives | None | Listed | Fair comparison with reasons | Includes the option the team would have picked by default, and beats it |
| Risk & rollout | Ignored | Generic risks | Named risks with mitigations | Rollout is reversible and observable, with explicit abort criteria |

## Mentor review prompts

- "What would have to be true for alternative B to be the right call?"
- "Which section does a new team member read first — and is it enough on its own?"
- "What did the early feedback change? If nothing: did you actually get it early enough?"
- "If this ships and breaks, what does the user see in the first minute?"

## Stretch 🔸

- Have someone else write the ADR using only your RFC. Diff their understanding against your intent — the gaps are what the RFC failed to say.
