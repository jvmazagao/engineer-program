# A3.6 — Load Test

## Why

Every service has a breaking point; most teams discover theirs from customers. A load test finds it on your schedule, and the capacity number ends the "can we handle Black Friday?" argument with data instead of vibes.

## Brief

Pick a real service endpoint — a read-heavy one for a first pass. Get approval for the target environment (staging with production-like data volume, or production in a safe window with explicit sign-off) and agree an abort threshold before starting.

**Scenario:** k6 or Locust script mimicking production shape — realistic payload sizes, read/write mix, think time, and a ramp: e.g. 10 → 100 → 500 RPS in steps, holding each step long enough to observe.

**Capture per step:** achieved RPS, p50/p95/p99 latency, error rate, and resource signals (CPU, memory, DB connections, queue depth).

**Find the first bottleneck** — the resource that saturates first — with evidence: the latency inflection should line up with the saturating metric, not just "it got slow".

**Capacity estimate:** max sustainable RPS at current size, plus what it takes to get 2× (instances, DB, cache) and what each option costs.

Compare the measured numbers against the estimates you made in A2.1 — explain the deltas.

## Tasks

- [ ] Get environment approval; agree the abort threshold and kill switch
- [ ] Write the scenario to match production traffic shape; state the rationale in the file
- [ ] Run the stepped load; capture RPS, p50/p95/p99, errors, and resource metrics per step
- [ ] Identify the first bottleneck with a resource metric as evidence, not just latency
- [ ] Produce the capacity estimate: current max, 2× options with cost
- [ ] Write the results note; compare against A2.1 estimates; share with the team

## Acceptance criteria

- [ ] Scenario file exists in a repo with the traffic-shape rationale documented
- [ ] Per-step numbers captured; the saturation point is visible in the data, not guessed
- [ ] The bottleneck claim is backed by a resource metric that saturates at the latency inflection
- [ ] Capacity estimate states its assumptions (payload size, data volume, instance type)
- [ ] Results note shared with the team; deltas vs. A2.1 estimates explained

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Scenario realism | Fixed loop, toy payloads | Ramped load, naive payloads | Matches prod shape (mix, payload sizes, think time) | Shape validated against real traffic logs |
| Measurement | Latency only | Latency + errors | + resource metrics per step | Latency inflection correlated with the saturating resource |
| Bottleneck | A guess | Plausible but unmeasured | Named resource with evidence | Confirmed by isolating it — fix one thing, rerun, see it move |
| Capacity | One number, no assumptions | Assumptions listed | Max RPS + a 2× path | 2× options costed; cheapest *correct* option identified |

## Mentor review prompts

- "Why did you pick this endpoint as representative of the service?"
- "Show me the moment the curve bent. What saturated first — and how do you know it isn't something downstream of it?"
- "Your A2.1 estimate versus the measurement: which was wrong, and why?"

## Stretch 🔸

- Find the second bottleneck behind the first, or promote the scenario to a nightly CI job that alerts on regression.
