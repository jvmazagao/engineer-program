# A3.1 — Observability Audit

← [[03 - Phase 3 - Production Ownership]] · Catalog: [[Assignments.base]]

| 3 — Production Ownership | end of week 29 | 🏭 at-work | ~4 h | mentor |

## Why

You can't own what you can't see. The gap between "we have dashboards" and "I can answer questions in an incident" is where most outages live — this audit measures it.

## Brief

Pick a service you own or work on daily. Name it; this audit is about *that* service, not observability in general.

Two passes:

**RED** — for each user-facing flow (top 3): does Rate, Errors, and Duration (p50/p95/p99) exist, measure the right thing, and can you find it in under 5 minutes?

**USE** — for each resource (app instances, database, cache, queue, disk): Utilization, Saturation, Errors — same three questions.

Then the honest part: list ≥10 questions a human would ask during an incident on this service — *"is it the DB or the code?" "when did this start?" "is anyone actually affected?" "did the last deploy change anything?"* — and mark each **answerable / not** with today's dashboards, logs, and traces. Every "not" is a gap.

Prioritise gaps by how often the question comes up × how expensive it is to answer blind. Output: an audit note + a prioritised top-5 gap list. Every gap claim must be tested — actually run the query or open the dashboard before marking something "answerable".

## Tasks

- [ ] Name the service and its top 3 user-facing flows
- [ ] RED check per flow: rate, errors, duration — exists? correct? findable in <5 min?
- [ ] USE check per resource: utilization, saturation, errors for app, DB, cache, queue
- [ ] Write the ≥10 incident questions and mark each answerable/not, with time-to-answer
- [ ] Test every "answerable" claim by actually running the query/dashboard
- [ ] Produce the prioritised top-5 gap list with effort estimates (S/M/L)
- [ ] Bring the #1 gap to the mentor session; agree what to instrument first (feeds week 30)

## Acceptance criteria

- [ ] Audit note names the service and links every dashboard/query checked
- [ ] ≥10 incident questions evaluated with yes/no and time-to-answer
- [ ] Both RED and USE covered — not just the metrics that already existed
- [ ] Gap list ≤5 items, each with priority justification and effort estimate
- [ ] At least one gap is a question you personally failed to answer in a real incident or on-call week

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Coverage | Only documented what already exists | RED only or USE only | Both, per flow and resource | Includes cross-service dependencies, not just the service itself |
| Honesty | Marked gaps as fine | Vague "probably fine"s | Clean yes/no per question | Every claim tested by actually running the query or dashboard |
| Prioritisation | No order | Ordered by gut | Frequency × cost-of-blindness reasoning | The gap that already burned the team is #1, with the story attached |
| Actionability | Wish list | Items without sizing | Sized items | #1 item scoped small enough to ship in week 30 |
