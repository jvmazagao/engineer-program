# A1.4 — Query Plan Lab

← [[01 - Phase 1 - Technical Depth]] · Catalog: [[Assignments.base]]

## Why

The two most valuable DB skills a senior uses weekly: reading a query plan instead of guessing, and knowing what your isolation level lets through. Both are done against your real system, because the plan and the anomalies only mean something on your schema and your data.

## Brief

Work in **a system you own at work**. Two parts.

**Part 1 — The plan.**

1. Pick the **slowest *frequent* query** — slow × often beats slow × once (skip one-off migrations and reporting dumps).
2. Run `EXPLAIN ANALYZE` (or your DB's equivalent) and save the plan.
3. Annotate every node: scan type (seq vs index), join type, estimated vs actual rows — flag any big estimate mismatch — and any sort/spill.
4. Propose an index (if you claim composite, justify the column order). Create it in dev, re-run the plan, compare.
5. Ship the migration if allowed; otherwise document the exact DDL you'd ship and why it's safe (write cost, size).
6. Write it up (`QUERY-PLAN.md`) so a teammate who doesn't know the schema can follow it.

**Peer part:** before the mentor session, your peer reads `QUERY-PLAN.md` cold and says where they got lost; you fix it. The peer is the readability check.

**Part 2 — Lost update under read committed.** In dev, two sessions side by side:

1. Both `SELECT` the same row (e.g., a balance or stock counter).
2. Both `UPDATE` it based on the value they read. Commit both.
3. Show that one update is silently gone. That's read committed.
4. Fix it two ways: `SELECT ... FOR UPDATE` and a single atomic `UPDATE ... SET x = x + 1 WHERE ...`. Re-run the demo, show both preserve both updates.
5. State which pattern your codebase actually uses today, and where.

## Tasks

- [ ] Identify the slowest frequent query; record volume and current latency
- [ ] Save and annotate the `EXPLAIN ANALYZE` plan, node by node, flagging estimate mismatches
- [ ] Propose, create (dev), and re-test an index; before/after plan and timing
- [ ] Ship migration or document exact DDL + safety notes
- [ ] `QUERY-PLAN.md` reviewed cold by peer; confusions fixed
- [ ] Two-session lost-update demo recorded (screenshots or transcript), then both fixes demonstrated
- [ ] Submission note: which isolation level your prod DB runs, and where your code relies on it

## Acceptance criteria

- [ ] Plan annotation covers every node, including est vs actual rows
- [ ] Index proposal justified (column order argued), with measured before/after
- [ ] Peer readability pass happened and its fixes are visible in the doc
- [ ] Lost update demonstrated under read committed, then prevented by both fixes, with evidence
- [ ] The "what our codebase does today" answer is verified in the code, not guessed

## Rubric (1–4)

| Criterion | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Plan reading | Plan not read | Scan types named only | Every node annotated | Estimate mismatches explained and acted on |
| Index proposal | "Add an index" with no specifics | Single-column guess, untested | Justified, tested, before/after shown | Order argued + write-cost/sizing considered |
| Lost-update demo | Not done | Described, not shown | Demonstrated + one fix | Demonstrated + both fixes + verified in real codebase |
| Communication | Schema-only insiders can read it | Correct but hard to follow | Peer-approved clarity | A new teammate could rerun the whole lab from the doc |

## Submit

Fill in your submission note under `Cohort/<you>/Submissions/`, link the doc, plans, migration/DDL, and demo evidence, set `state: submitted`.

## Mentor review prompts

- "Point at the node that dominated the first plan. What was it doing with its time?"
- "Why did the planner pick a seq scan — stats, selectivity, or no index?"
- "What's the write cost of the index you added, and who pays it?"
- "In the lost-update demo: why doesn't read committed stop it? What's the *lowest* isolation that would?"
- "Where in our code is the read-modify-write pattern live right now?"

## Stretch 🔸

- Force the planner to ignore your index (hint or `SET enable_seqscan`) and explain when you'd actually *want* it ignored. Or: demonstrate the same lost update with an ORM and show which ORM-level fix maps to which SQL fix.
